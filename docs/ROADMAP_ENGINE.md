# Roadmap Engine — Design & Reference (Phase 5)

The personalized learning roadmap is a **deterministic, local-first engine**. It converts the
imported curriculum into a week-by-week study plan from the learner's profile, schedule, and
real completion data. **No LLM is involved**: same inputs always produce the same plan.

---

## 1. Career Tracks

Tracks are **configuration, not code**. Seven tracks ship in `roadmaps/tracks/*.json` and are
loaded by `src/lib/roadmap/config.ts`; adding a track requires only a new JSON file plus
lesson-importance data, no React changes:

| Track | JSON | Focus |
| --- | --- | --- |
| General AI Engineer | `general-ai.json` | Breadth across the full curriculum |
| LLM Application Engineer | `llm-app-engineer.json` | Prompting, evaluations, LLM apps |
| RAG Engineer | `rag-engineer.json` | Embeddings, vector search, retrieval pipelines |
| Agent Engineer | `agent-engineer.json` | Tool use, planning, multi-agent systems |
| ML Engineer | `ml-engineer.json` | Classical ML → deep learning foundations |
| MLOps / AI Infrastructure Engineer | `mlops-engineer.json` | Deployment, monitoring, infrastructure |
| Research-Focused AI Engineer | `research-ai-engineer.json` | Papers, math, architecture depth |

Each track declares `coreSkills`, `targetRoles`, `majorProjects`, and per-occurrence
importance (`core | important | optional | skip`). Skipped lessons are **never deleted from
the curriculum** — they are simply not scheduled.

## 2. Occurrence vs. Canonical Identity

The curriculum has **542 parsed locations but 541 canonical lessons**. The two
Vision-Transformer entries (`04-computer-vision/14-vision-transformers` and
`07-transformers-deep-dive/09-vision-transformers`) are distinct curriculum occurrences that
share one canonical progress identity.

Roadmap nodes therefore carry both identifiers:

```ts
{
  curriculumOccurrenceId: string, // e.g. "04-computer-vision/14-vision-transformers"
  canonicalLessonId: string,      // shared progress key
  phaseSlug: string,
  lessonSlug: string
}
```

Rules:

- **Ordering and prerequisites operate on curriculum occurrences.** Both VT occurrences
  exist independently in the roadmap graph; neither can silently disappear.
- **Completion is resolved through `canonicalLessonId`.** Completing one occurrence
  satisfies the shared canonical progress identity, so the twin occurrence is recognized as
  satisfied in scheduling while still remaining visible in the graph.
- Phase 0–4 progress UUIDs are unchanged; the roadmap reads existing completion records.

## 3. Metadata Layer

`roadmaps/metadata/lesson-metadata.json` (generated by `src/scripts/roadmap-generate-metadata.ts`
from upstream lesson data, then curated) stores per occurrence:

- `importanceByTrack` (seven-track importance map)
- `prerequisites`, `recommendedBefore`
- `difficulty` (`beginner | intermediate | advanced`)
- `estimatedMinutes` (upstream duration when available, else the centralized fallback
  `DEFAULT_DURATION` in `src/lib/roadmap/config.ts`: beginner 45 / intermediate 60 /
  advanced 90; projects have separate effort estimates)
- `skillTags` (cross-referenced with `roadmaps/skills/taxonomy.json`)
- `projectRelevant`, `optionalReason`

The UI displays estimates as approximations (`~1h`), never fake precision like "57 minutes".

## 4. Prerequisite Graph

`src/lib/roadmap/graph.ts` builds a DAG over occurrences and supports:

- topological sort (deterministic tie-breaking)
- cycle detection — a cycle **fails validation** (`npm run roadmap:validate`) and names the
  exact nodes; invalid graphs are never scheduled
- missing-prerequisite detection
- prerequisite explanation ("X is scheduled before Y so that Y's prerequisites hold")
- reachable-node calculation

## 5. Scheduling Algorithm

`src/lib/roadmap/scheduler.ts` takes learner inputs (track, `availableHoursPerWeek`,
`startDate`, `targetDate`, `studyDays`, buffer preferences, completed/mastered canonical
lesson keys, optional-topic inclusion, manual includes/excludes) and emits a week-by-week
plan:

1. Compute importance filtering for the track (skip → excluded, optional honoured only when
   `includeOptionalTopics`).
2. Topologically order the remaining occurrences (completions pin satisfied nodes).
3. Walk weeks: allocate parts of each lesson across study days, splitting long lessons into
   parts (`Part 2 of 3`) rather than overfilling weeks. Weekly capacity is never exceeded
   unless the learner explicitly allows it.
4. Insert buffer weeks per the preference (automatic monthly, manual, none).
5. Summarize totals for the capacity analysis.

Output is **deterministic for identical inputs** — no randomness, no wall-clock dependence
beyond the declared start date.

## 6. Capacity Analysis

`src/lib/roadmap/capacity.ts` compares required vs. available study hours and returns a
feasibility status:

- **Comfortable** — ample slack
- **Achievable** — fits with modest slack
- **Tight** — roughly at capacity; options shown (more hours, later target, drop optionals)
- **Unrealistic** — capacity clearly short of the workload

The engine never silently compresses lessons; the UI surfaces the shortfall and the options.

## 7. Buffer Weeks

Supported: automatic monthly buffers, manually added buffer weeks, and named special weeks
(holidays, exams, vacations). Buffer weeks contain **no mandatory new content** unless the
learner explicitly assigns catch-up work to them.

## 8. Rescheduling

`src/lib/roadmap/rescheduler.ts` recalculates only the plan from today forward:

- Finished weeks are **never rebuilt**.
- Completed and mastered canonical lessons keep their completion status (history is
  immutable through a reschedule).
- Missed (past and unfinished) lessons move into a **backlog**, ordered by prerequisite
  impact: blocking core work first, then core, important, optional.
- Learners can adjust hours per week, target date, or drop optional content from the
  reschedule dialog, which previews the week-count and projected end-date impact first.

## 9. Onboarding & Placement

`/onboarding` collects, in seven steps: background, programming self-assessment, math
self-assessment, AI/ML self-assessment, goal track, schedule (hours/week, study days, start
and target dates, buffer preference), and existing-experience topics.

The optional deterministic **placement assessment** (`src/lib/roadmap/placement.ts`, backed
by `/api/roadmap/placement` serving imported quiz questions) recommends a starting phase,
review-first topics, and safe-to-skim lessons from self-assessment plus quiz answers. It
**never marks lessons complete**; the learner can override its recommendation at any time.

## 10. Skill Taxonomy

`roadmaps/skills/taxonomy.json` defines the skill groups (programming, math, ML foundations,
LLM/RAG/agents, deployment) and individual skills that metadata `skillTags` reference. Skill
progress on `/roadmap` is computed from **real activity** (lesson completions), never from
self-assessment alone.

## 11. Persistence & Determinism

- Profile, placement, settings, manual includes/excludes, and the generated plan persist in
  the same local-first Dexie store used by Phase 0–4 progress; roadmap state syncs through
  the Phase 4 account-sync system unchanged.
- Guests get full roadmap functionality with local persistence.
- `npm run roadmap:validate` and `npm run roadmap:coverage` (reports in
  `reports/roadmap-coverage.md`) gate data quality in CI.

## 12. Testing

- Unit: graph (topo/cycles/missing prereqs), scheduler, capacity, rescheduling, placement,
  tracks, skills, persistence, VT twin-occurrence identity (`src/test/roadmap-*.test.ts`).
- Playwright journeys: new learner onboarding → roadmap, lesson progress reflected on the
  roadmap, backlog + reschedule with preserved history, track comparison and switch
  (`e2e/roadmap-*.spec.ts`).
